# 角色、数据与操作权限矩阵

## 1. 一期权限原则

1. 所有登录用户均可修改其数据范围内可见患者的业务信息（已确认）。
2. 一期不实施细粒度字段编辑隔离；保留导入、导出、推送和系统管理权限（已确认）。
3. 查询、修改和导出必须使用同一 `DataScope`；修改 SQL 自身必须带范围条件。
4. 一个用户可拥有多个角色；新用户默认无角色，由系统管理员分配。
5. `SYSTEM_ADMIN` 拥有全部数据和全部操作权限。
6. 多角色的操作权限取并集，数据范围取并集，但仍须通过接口权限校验（已确认）。

> 现有代码仍强制检查部分 `FIELD_*` 权限，与一期已确认规则冲突，后续阶段应直接按基线整改，见《10-现状差异清单》。

## 5. 数据范围验收规则

- 系统管理员应能访问所有科室、所有医生数据。
- 科主任只能访问其角色配置的科室；配置多个科室时取并集。
- 主管医生只访问通过工号唯一匹配到本人用户 ID 的患者；待匹配患者不归任何主管医生个人范围。
- 列表、导出、修改、统计使用一致范围；统计默认按 `DataScope` 过滤，系统管理员和运营部可查看全院统计（已确认）。
- 科主任和主管医生允许导出本人可见范围，导出必须记录完整审计日志（已确认）。
- 无权访问的资源建议返回 `403`；为避免泄露资源存在性，也可统一返回 `404`，需接口规范统一。
- 影响行数为 0 的越权修改必须失败，不能返回成功。

## 6. 权限编码基线

现有权限包括：`MENU_ARREARS`、`MENU_DISCHARGE`、`MENU_SYSTEM`、`API_USER_MANAGE`、`API_ROLE_MANAGE`、`API_ARREARS_EDIT`、`API_DISCHARGE_EDIT`、`API_PUSH_RETRY`、`API_ARREARS_IMPORT`、`API_ARREARS_EXPORT`、`API_ARREARS_REPORT`、`API_DISCHARGE_IMPORT`、`API_DISCHARGE_EXPORT`、`API_DISCHARGE_ANALYSIS`、`API_FEE_CONFIG`、`API_DEPT_MANAGE`、`API_AUDIT_VIEW`。

Spring Security 实际加载为 `PERM_<permission_code>`；角色加载为 `ROLE_<role_code>`。前后端必须保持该前缀规则一致。

阶段 2 已通过 Flyway V10 为运营部、财务科、科主任和主管医生配置相应业务权限，并修正认证加载逻辑，确保 `ROLE_*` 与 `PERM_*` 同时生效。系统管理员、运营部和财务科为全量数据范围；科主任和主管医生仍分别受科室与本人患者范围限制。
