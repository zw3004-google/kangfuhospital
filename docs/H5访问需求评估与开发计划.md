# 康复医院运营管理系统 H5 访问需求评估与开发计划

> 编制日期：2026-09-05
> 评估对象：当前 `web/` Vue 3 管理端与 `server/` Spring Boot 服务端
> 目标定义：支持院内用户通过手机浏览器或企业微信内置浏览器完成高频移动办公；本计划不包含微信小程序和原生 App。

## 1. 结论摘要

当前系统具备 H5 改造的良好业务和后端基础，但前端尚未达到手机端可用标准。

- 可复用：现有 Vue 3、TypeScript、Vue Router、Element Plus、ECharts、Axios，以及后端接口、数据权限、字段权限、审计、导入导出和企业微信推送逻辑。
- 主要差距：应用外壳设置了 `min-width: 1180px`；核心业务大量使用宽表格、固定列、固定宽度筛选器和桌面弹窗；除登录页和部分统计样式外，缺少完整的移动端布局与交互规则。
- 推荐方案：保留一个前端工程和一套业务接口，建立响应式应用壳层，并为高频业务提供移动端卡片列表、抽屉/全屏表单和简化筛选。不要复制一套独立 H5 代码库。
- 推荐首期范围：登录与改密、工作台、欠费查询与业务处理、预计出院查询与分角色填报、统计概览、推送记录只读查询，以及系统管理页面的移动适配。
- 明确排除：数据导入、文件导出和批量重试；企业微信免登录、角色待办首页也不纳入一期。
- 预计投入：包含系统管理移动适配后约 110～145 人日，建议 2 名前端、1 名后端、1 名测试，产品/设计与运维兼职参与，日历周期 9～11 周。

## 2. 当前系统基线

### 2.1 技术与业务现状

- 前端：Vue 3.5、TypeScript、Vite 7、Element Plus 2.11、ECharts 5.6。
- 后端：Java 21、Spring Boot、Spring Security、PostgreSQL、Flyway。
- 前端共 15 个视图，现有路由覆盖登录、工作台、欠费、预计出院和系统管理。
- 9 个视图包含数据表格，9 个视图包含弹窗，2 个视图包含文件上传，约 6 个视图包含下载或导出行为。
- 当前权限包含菜单、路由、按钮、数据范围和字段级控制；H5 必须沿用后端鉴权，不得仅依赖前端隐藏。
- 系统规模基线为并发登录不超过 100、单批导入不超过 1000 条，现有后端容量无需因 H5 单独拆分。

### 2.2 移动端差距

| 领域 | 当前情况 | H5 影响 | 改造等级 |
|---|---|---|---|
| 应用框架 | 左侧栏固定 236px，应用最小宽度 1180px | 手机产生整页横向滚动 | 必须改造 |
| 导航 | 桌面左侧分组菜单 | 单手操作困难 | 改为顶部栏 + 抽屉菜单 |
| 数据列表 | 大量宽表格、左右固定列 | 信息不可读，触控目标过密 | 核心页改卡片；次要页允许局部横滑 |
| 筛选 | 多控件横向排列且固定宽度 | 小屏溢出 | 简单筛选外露，高级筛选进抽屉 |
| 编辑 | 桌面弹窗、双列表单 | 键盘遮挡、内容超高 | 手机使用全屏抽屉/独立详情页、单列布局 |
| 图表 | 已监听窗口变化，部分断点已存在 | 基础较好，仍需触控和标签适配 | 中等改造 |
| 上传下载 | 浏览器文件选择和 Blob 下载 | 企业微信内置浏览器、iOS 下载兼容性不确定 | 专项验证；首期限制批量操作 |
| 登录会话 | Session Cookie + CSRF，30 分钟服务端超时，Basic 已关闭 | 本地安全整改完成，目标环境待验收 | 阶段 4 验证 |
| 浏览器支持 | 已配置 viewport，未声明支持矩阵 | 兼容性不可验收 | 建立支持矩阵和真机测试 |
| 可用性 | 未见全局移动断点、触控尺寸和安全区规范 | 刘海屏、软键盘和误触风险 | 必须补齐 |

## 3. 目标用户与移动场景

### 3.1 优先用户

1. 主管医生：查询本人患者、填写预计出院信息、查看异常和随访情况。
2. 科主任：查看本科室患者、欠费与预计出院概况，处理本科室事项。
3. 运营部/财务科：移动查看欠费、通报和推送状态，执行轻量业务处理。
4. 门诊部、营养科、居家康复科、随访员：在患者详情中填写职责范围内字段。
5. 系统管理员：主要继续使用桌面端，手机端只保留账户与紧急只读能力。

### 3.2 典型场景

- 从企业微信消息链接进入系统，登录后直达指定患者或待办页面。
- 在病区移动查找患者，查看欠费、预计出院、异常和预约信息。
- 在手机上完成少量字段填报、保存和查看修改历史。
- 查看科室/个人概览、统计趋势与推送结果。
- 网络短时中断时明确提示，防止重复提交；首期不承诺离线编辑。

## 4. 建议功能范围

### 4.1 P0：首期必须交付

| 模块 | H5 功能 | 主要改造 |
|---|---|---|
| 登录与安全 | 登录、首次改密、退出、超时提示、无权限页 | 移动键盘适配、错误提示、返回路径、会话方案调整 |
| 应用壳层 | 响应式顶部栏、抽屉导航、页面标题、用户信息 | 去除全局最小宽度，处理安全区和横竖屏 |
| 工作台 | 角色相关模块入口和统计摘要 | 单列或双列卡片，避免展示无权限入口 |
| 欠费明细 | 查询、筛选、分页、摘要、详情、授权字段编辑、历史 | 表格转卡片列表，详情全屏化，高级筛选抽屉化 |
| 预计出院 | 查询、筛选、摘要、患者详情、分角色字段填报、历史 | 患者卡片、职责分区、单列表单、保存防重 |
| 统计概览 | 关键指标、趋势、分类切换、明细下钻 | 图表触控、标签精简、明细卡片化 |
| 通用体验 | 加载、空状态、失败重试、网络异常、二次确认 | 统一反馈与防重复提交 |
| 权限与审计 | 复用现有权限与审计 | 对 H5 路由、按钮和字段做角色回归 |

### 4.2 P1：一期同时交付的系统管理能力

- 用户、角色、权限、科室和费别系数的查询与维护。
- 审计日志查询与详情查看。
- 复杂权限矩阵在手机端采用分组、折叠和分步提交，不直接压缩桌面布局。
- 系统管理属于低频、高风险操作，需增加二次确认、保存防重和并发冲突提示。

### 4.3 P2：建议二期交付

- 通报报表完整移动版和通知预览，不包含文件导出。
- 欠费/预出院推送记录详情、尝试历史和单条重试，不包含批量重试。
- 导入批次与错误明细只读查询，不包含发起导入。
- 企业微信 OAuth/免登或单点登录，以及消息直达患者的深链接。
- PWA 桌面图标、版本更新提示；是否启用需结合医院终端管理策略。

### 4.4 明确排除或后续评估

- XLSX 批量导入、文件导出及文件二次处理。
- 批量推送重试。
- 离线填报、拍照上传、语音输入、原生扫码等原生能力。

## 5. 非功能需求

### 5.1 终端与浏览器

- 目标宽度：360px～430px 手机为主，兼容 768px 平板；桌面现有能力不得退化。
- 推荐最低版本：iOS 15 及以上的 Safari；Android 10 及以上、Chrome 100 及以上；企业微信采用医院当前统一版本及其前一个主要版本。不针对老旧 Android Browser 或 IE 做适配。
- 推荐验收设备至少覆盖：一台 375px 左右 iPhone、一台 390px/430px iPhone、一台主流 360px/393px Android 手机和一台 768px 左右平板；医院实际配发量最大的 iOS、Android 设备必须各纳入一台。
- 兼容横竖屏，但核心填报以竖屏为验收基准。
- 触控目标建议不小于 44×44px；正文不小于 14px；金额、状态和关键风险信息不可仅以颜色区分。

### 5.2 性能

- 首屏静态资源按路由拆包并压缩；建议移动网络下首屏可交互时间不超过 3 秒，院内 Wi-Fi 下不超过 2 秒。
- 列表默认 20 条/页；避免在手机端一次渲染 50～200 条复杂记录。
- 图表和详情按需加载；重复查询可取消旧请求。
- 建立前端异常、接口耗时和版本号观测，日志不得包含密码和完整敏感患者信息。

### 5.3 安全与隐私

- 全链路 HTTPS；禁止通过公网无 VPN 直接暴露系统。
- 已完成 Session Cookie + CSRF 认证整改，关闭 Basic；保留 HttpOnly、SameSite，正式 HTTPS 必须启用 Secure。详见 [CSRF 与 Session 整改记录](h5/H5-CSRF与Session认证整改计划.md)。
- 企业微信免登需在后端完成 code 换取身份、用户绑定和状态校验，Secret 只保存在服务端。
- 深链接进入患者详情时仍必须执行 `DataScope` 和字段权限校验。
- 一期默认只展示业务所需且已授权的患者字段，列表隐藏非必要敏感详情，并叠加当前登录人和时间的低干扰动态水印。
- H5 无法可靠阻止系统截屏，因此不承诺“禁止截屏”。通过管理制度、动态水印和审计追责降低风险；不建议全局禁用复制，可只限制身份证号、联系电话等高敏感字段（若系统后续展示）。
- 页面切到后台时遮盖业务内容，重新回到前台后恢复；超过现有 30 分钟空闲时间必须重新登录。操作系统任务切换器缩略图无法在所有浏览器上完全控制，需真机验证。

### 5.4 可用性与数据完整性

- 保存按钮防重复点击；更新失败不得清空用户已填写内容。
- 对关键状态变更提供确认和明确结果；并发编辑建议引入版本号或更新时间冲突检测。
- 页面刷新、登录过期后尽量恢复原目标路由和非敏感筛选条件。
- 不提供离线提交；断网时明确显示未保存状态。
- 一期引入乐观锁：业务记录增加版本号或使用更新时间作为条件更新，版本不一致时提示用户刷新后重试，避免后保存的数据静默覆盖先保存的数据。
- 编辑表单在当前会话内自动保存非敏感草稿，提交成功后清除。草稿不长期保存，退出、超时或切换用户时必须清除；患者敏感字段不写入长期浏览器存储。

## 6. 技术方案

### 6.1 推荐架构

采用“同一 SPA、同一路由、按断点切换展示组件”的渐进式方案：

```text
手机/企业微信浏览器 ─┐
                     ├─ Vue 3 单一前端 ─ /api ─ Spring Boot ─ PostgreSQL
桌面浏览器 ──────────┘       │
                             └─ 同一权限、审计、接口和发布版本
```

原则：

- 业务请求、类型、校验与权限逻辑共用；只分离桌面表格和移动卡片等展示组件。
- 建立 `useBreakpoint`、移动导航、筛选抽屉、患者卡片、移动详情容器等通用能力。
- 不通过 UA 判断核心业务，主要使用 CSS media query 和容器宽度；仅对企业微信兼容行为做能力检测。
- 现有 Element Plus 可继续使用，但需要统一移动主题覆盖并逐项验证日期、选择器、弹窗和分页组件。
- 首期原则上不新增业务接口；可为移动工作台、轻量列表和详情聚合增加少量 BFF 风格接口，减少请求数和冗余字段。

### 6.2 列表改造规则

- 手机端卡片首屏只展示姓名/住院号、科室/医生、金额或出院时间、状态/异常、主操作。
- 其余字段进入详情，避免把桌面 10～20 列全部塞入手机列表。
- 卡片整行可点击，关键操作保留独立按钮；危险操作不得使用滑动手势作为唯一入口。
- 分页使用“加载更多”或简化分页；筛选条件变更后回到第一页。

估算假设：复用现有后端业务规则和视觉语言，不包含业务范围扩张、原生 App、小程序、离线能力及 HIS 新接口。

| 工作包 | 估算人日 |

| 登录、改密、工作台 | 5～7 |
| 欠费明细移动版 | 10～14 |
| 预计出院移动版及多角色填报 | 14～18 |
| 统计分析、通报概览、推送记录 | 10～14 |

## 8. 建议开发计划

### 阶段 H0：需求冻结与原型（第 1 周）

- 访谈主管医生、科主任、财务/运营、门诊/营养/居家/随访人员。
- 确认 P0 页面、字段优先级、手机可编辑动作、敏感信息展示和浏览器矩阵。
- 输出关键页面低保真原型、角色任务流和验收用例。
- 技术验证目标手机浏览器及企业微信内置浏览器的登录、日期控件、导航返回和会话行为。

退出标准：范围、原型、认证路线和验收矩阵签字确认。

实施状态（2026-09-05）：本地交付物已完成，未部署测试环境。需求与验收基线见 `h5/H0-需求与验收基线.md`，交互原型见 `h5/h0-mobile-prototype.html`。业务负责人、UAT 代表、医院实机型号和内网 HTTPS 证书方案可在 H1 结束前补齐。

### 阶段 H1：移动基础与安全（第 2 周）

- 响应式壳层、抽屉导航、全局断点、安全区和通用移动组件。
- 调整会话存储方案、登录过期回跳和统一网络错误处理。
- 建立 375px/390px/768px 组件测试和关键页面截图基线。

退出标准：登录、导航、权限、异常反馈在目标终端通过冒烟测试，桌面端无回归。

实施状态（2026-09-05）：本地实现与自动化验证已完成，未部署测试环境。详见 `h5/H1-本地实施记录.md`。真实手机、内网 HTTPS、Cookie 与 CSRF 生产门禁留待部署前验证。

### 阶段 H2：核心业务一（第 3～4 周）

- 完成欠费明细卡片列表、筛选、摘要、详情、编辑和历史。
- 完成预计出院卡片列表、筛选、摘要和详情骨架。
- 补充移动列表接口或字段裁剪（若性能测试证明需要）。

退出标准：系统管理员、财务/运营、科主任、主管医生数据范围及操作权限自动化通过。

实施状态（2026-09-05）：本地实现与自动化验证已完成，未部署测试环境。详见 `h5/H2-本地实施记录.md`。真实手机和测试环境角色联调留待后续统一执行。

### 阶段 H3：核心业务二（第 5～6 周）

- 完成预计出院多角色分区填报和表单校验。
- 完成统计概览、趋势触控、明细下钻和推送记录只读查询。
- 完成保存防重、乐观锁、会话内草稿和审计验证。

退出标准：主管医生、门诊部、营养科、居家康复科、随访员的字段权限和端到端场景通过。

实施状态（2026-09-05）：本地实现与自动化验证已完成，未部署测试环境。详见 [H3 本地实施记录](h5/H3-本地实施记录.md)。真实手机及五类岗位账号端到端 UAT 留待 H5。

### 阶段 H4：系统管理移动适配（第 7～8 周）

- 完成用户、角色、权限、科室、费别系数和审计日志移动适配。
- 高风险管理操作增加二次确认、并发冲突提示和审计验证。
- 完成系统管理员专项回归。

退出标准：管理员可在目标手机上完成一期约定的全部管理操作，权限矩阵无越权或误覆盖。

实施状态（2026-09-05）：本地实现与自动化验证已完成，未部署测试环境。详见 [H4 本地实施记录](h5/H4-本地实施记录.md)。真实手机和管理员真实账号 UAT 留待 H5。

### 阶段 H5：兼容、UAT 与上线（第 9～10 周）

- 弱网、超时、横竖屏、软键盘、返回键、重复提交和长文本专项测试。
- 五类业务角色及系统管理员 UAT、缺陷整改、灰度部署、培训和回滚演练。
- 先对少量科室灰度 3～5 个工作日，再扩大范围。

退出标准：P0/P1 缺陷关闭，核心用例 100% 通过，性能与安全门禁通过，业务和信息科签署上线。

实施状态（2026-09-05）：本地兼容加固、自动化回归、CSRF/Session 整改和阶段 4 本地浏览器/并发验收已完成，未部署测试环境；真机、院内网络、UAT、目标环境 HTTPS 安全验收、灰度和签署仍未完成，因此 H5 总体验收保持待完成。详见 [H5 本地实施记录](h5/H5-本地实施记录.md) 和 [UAT 与上线检查清单](h5/H5-UAT与上线检查清单.md)。

## 9. 验收标准

### 9.1 功能验收

- 360px 宽度下核心页面无整页横向滚动；允许经设计确认的数据容器局部横滑。
- 各角色仅看到授权菜单、患者和字段；直接输入 URL 及直接调用 API 均不能越权。
- 欠费和预计出院的查询、详情、编辑、历史与桌面端数据一致。
- 保存、失败重试、登录超时、无权限和网络中断均有清晰反馈。
- 关键操作均产生与桌面端一致的审计记录。

### 9.2 质量门禁

- 现有后端、前端单元测试和生产构建全部通过。
- 新增核心移动组件测试、路由/权限测试和至少一组端到端自动化。
- 支持矩阵内真机核心用例全部通过；不存在未关闭 P0/P1 缺陷。
- Lighthouse 或等效测试用于趋势门禁；以真实院内网络和目标设备结果为最终依据。
- 安全检查覆盖认证存储、会话失效、CSRF/XSS、越权、敏感信息日志和 HTTPS 配置。

## 10. 主要风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 把桌面表格直接缩放到手机 | 可读性和效率严重下降 | 按角色确定首要字段，核心列表改卡片和详情分层 |
| 企业微信浏览器行为差异 | 登录、下载、返回行为异常 | 第 1 周完成真机技术验证，下载类功能设桌面兜底 |
| 移动会话与请求伪造风险 | 移动终端丢失或恶意跨站写入 | Session + CSRF 已完成本地改造，目标 HTTPS 和真机安全门禁待验收 |
| 多角色字段过多 | 表单冗长、误填 | 按权限只展示职责分区，使用分段保存或吸底操作栏 |
| 桌面与移动双视图逻辑分叉 | 后续维护成本上升 | 请求、校验、权限与类型共用，仅拆展示组件 |
| 未做真实用户移动 UAT | 上线后操作流程不符合病区习惯 | 每类角色至少 1～2 名代表参与原型和灰度验收 |
| 医院网络或证书问题 | 手机无法访问或接口不稳定 | 提前验证 Wi-Fi/VPN、DNS、HTTPS 证书链和防火墙 |

## 11. 已确认事项与启动条件

截至 2026-09-05 已确认：

1. H5 仅限院内网访问，不强制通过企业微信入口。
2. 一期不实现企业微信免登录，继续使用账号密码登录。
3. 一期排除导入、导出和批量重试。
4. 支持矩阵采用本计划第 5.1 节推荐值，并在 H0 阶段用医院主流实机补齐具体型号。
5. 手机敏感信息默认采用“权限控制 + 最小展示 + 动态水印 + 切后台遮盖”；不承诺禁止系统截屏，不全局禁用复制。
6. 系统管理页面一期支持移动端，因此需要计入范围和工作量。
7. 一期工作台维持模块入口，不开发角色待办和待办聚合接口。
8. 一期实现并发编辑冲突检测和保存失败草稿：采用乐观锁与会话内临时草稿，不长期保存患者敏感数据。

上述信息已经达到启动开发的条件。启动后 H0 阶段仍需完成以下细化项，但不阻塞立项和基础框架开发：

- 指定业务负责人、信息科负责人及各角色 UAT 代表。
- 确认医院主流测试机型和院内 Wi-Fi 测试区域。
- 审阅关键页面低保真原型，确认移动列表首要字段和系统管理操作流程。
- 确认 HTTPS 内网域名及移动终端对证书链的信任方式。

## 12. 建议立项口径

建议以“移动办公适配一期”立项，而不是“全站页面 H5 化”：

- 目标：让业务人员在手机上完成查询、查看、少量填报和待办处理。
- 范围：P0 核心业务、系统管理移动适配及必要的认证、安全和并发控制改造；排除导入、导出、批量重试、免登录和角色待办。
- 团队：2 前端 + 1 后端 + 1 测试，产品/设计、运维和安全兼职。
- 周期：9～11 周，建议承诺 10 周、预留 1 周机动。
- 预算基线：110～145 人日；H0 原型确认后做二次估算。
