# 欠费推送记录原型对齐修改计划

> 制定日期：2026-09-02  
> 当前状态：**阶段 1～7 已完成，自动化验收通过**  
> 本轮范围：阶段 7 已完成 PostgreSQL 集成回归、前端全量测试、类型检查和生产构建

## 一、整改目标

将欠费管理下的“推送记录”由技术任务列表调整为面向业务人员的推送留痕页面，同时保留现有的发送尝试历史、自动重试和人工重发能力。页面与接口必须使用一致的数据范围，确保科主任只能访问配置科室相关推送，主管医生只能访问本人相关推送。

本次对齐不增加渠道筛选，也不在列表展示渠道列。底层发送渠道仍为企业微信，但不作为页面查询维度。

## 二、阶段 1：已确认业务口径

### 2.1 页面结构

1. 页面保留筛选区和“推送留痕”列表区。
2. 筛选项仅包含状态和推送日期范围，不提供渠道筛选。
3. 列表不展示渠道列。
4. 保留分页、发送尝试详情、重试次数和最近错误。
5. 有重发权限的用户可对失败记录执行单条重发或勾选后批量重发。
6. 无重发权限的用户以只读方式访问，不显示选择框和重发操作。

### 2.2 页面状态口径

页面状态筛选固定为：

- 全部状态
- 发送中
- 重试中
- 成功
- 失败

页面业务状态与数据库技术状态按下表转换：

| 页面状态 | 数据库状态 | 处理规则 |
|---|---|---|
| 发送中 | `PENDING`、`SENDING` | 等待调度和已被调度器领取统一展示为“发送中” |
| 重试中 | `RETRYING` | 首次或中间发送失败，正在等待自动重试 |
| 成功 | `SENT` | 已成功发送 |
| 失败 | `FAILED` | 自动重试结束后仍失败，可人工重发 |

`CANCELLED` 继续作为数据库兼容状态保留，但不进入状态筛选项。后续查询实现不得将其错误映射为“失败”。历史数据若存在该状态，默认在“全部状态”中显示为“已取消”，且不允许重发；如实施时确认数据库不存在历史取消任务，可通过明确条件排除，但不得静默改写状态。

后端继续保留全部技术状态，前端只使用中文业务状态，不直接展示英文枚举。

### 2.3 推送时间口径

1. 页面筛选字段统一命名为“推送日期”。
2. 页面列表字段统一命名为“推送时间”。
3. 成功任务使用 `sent_at` 作为推送时间。
4. 未成功任务使用 `scheduled_at` 作为推送时间。
5. 查询和排序统一按 `COALESCE(sent_at, scheduled_at)` 执行。
6. 开始日期包含当日 `00:00:00`，结束日期包含当日全部时间，接口实现建议使用“结束日期次日零点之前”的左闭右开范围。
7. 未填写日期时不限制时间范围；只填写一端时按单边条件查询。

### 2.4 数据范围

欠费推送记录沿用项目既有 DataScope 规则：

| 角色 | 查看范围 | 重发权限 |
|---|---|---|
| 系统管理员 | 全院欠费推送 | 有 |
| 运营部 | 全院欠费推送 | 有 |
| 财务科 | 全院欠费推送 | 有 |
| 科主任 | 角色配置的一个或多个科室相关推送，多个科室取并集 | 无 |
| 主管医生 | 与本人 `doctor_user_id` 相关或直接发送给本人的推送 | 无 |
| 其他角色 | 默认无权访问，按后续正式授权决定 | 无 |

列表、任务详情、发送尝试详情、单条重发和批量重发必须使用同一套数据范围校验。前端隐藏按钮不代替后端鉴权。

现有 `push_task` 未保存足够的结构化业务范围，后续阶段必须补充接收用户及科室/主管医生关联。不得依赖接收人姓名或消息正文推断数据范围。

### 2.5 推送内容范围

1. 面向科主任生成的内容只能包含其配置科室范围内的数据。
2. 面向主管医生生成的内容只能包含与本人关联的患者数据。
3. 系统管理员、运营部、财务科可使用全院范围内容。
4. 推送任务创建时应同时固化接收用户、业务范围和实际发送内容，保证历史记录可追溯。
5. 页面显示的内容摘要必须来源于该任务实际保存的内容，不重新使用当前实时数据拼接。

### 2.6 列表字段

目标主列表字段顺序为：

1. 选择框，仅有重发权限时显示；
2. 推送时间；
3. 接收人；
4. 推送内容；
5. 状态；
6. 触发方式；
7. 重试次数；
8. 最近错误；
9. 操作。

触发方式显示规则：

- `AUTOMATIC` 显示“系统自动”；
- `MANUAL` 显示“人工重发”。

内容较长时列表显示摘要，完整实际发送内容在详情中查看。最近错误仅作为诊断摘要展示，完整错误码和错误信息继续在发送尝试详情中展示。

### 2.7 重发规则

1. 只有 `FAILED` 任务允许人工重发。
2. 科主任和主管医生不能执行单条或批量重发。
3. 批量重发只处理用户明确勾选的任务 ID，不得默认处理当前业务下全部失败任务。
4. 一期批量选择限定当前页，不支持跨页保留选择。
5. 单条和批量重发均需二次确认。
6. 服务端逐条校验任务存在性、业务类型、当前状态、操作权限和数据范围。
7. 重发不得删除或覆盖既有发送尝试，必须追加新的人工尝试并保留审计记录。
8. 批量接口返回成功、跳过和失败数量；不符合条件的任务不得被更新。

### 2.8 权限拆分

后续实施将查看权限和重发权限拆分：

- `API_PUSH_RECORD_VIEW`：访问推送记录列表和发送尝试详情；
- `API_PUSH_RETRY`：执行单条和批量人工重发。

页面路由使用查看权限，重发按钮和重发接口使用重发权限。科主任、主管医生可授予查看权限，但不授予重发权限。

## 三、接口约定草案

### 3.1 列表查询

```text
GET /api/arrears/push-records
  businessType=ARREARS
  status=SENDING|RETRYING|SUCCESS|FAILED
  startDate=2026-07-01
  endDate=2026-08-03
  page=1
  pageSize=50
```

其中 `status=SENDING` 是页面业务状态，服务端转换为 `PENDING`、`SENDING` 两个数据库状态；`SUCCESS` 转换为 `SENT`。接口不接受渠道参数。

列表返回至少包含：

```text
id
businessType
reminderType
contentSummary
recipientName
status
displayStatus
triggerType
scheduledAt
sentAt
pushTime
retryCount
lastError
```

### 3.2 批量重发

```text
POST /api/arrears/push-records/retry-batch
Content-Type: application/json

{
  "businessType": "ARREARS",
  "ids": [101, 105, 108]
}
```

返回至少包含：

```text
requestedCount
successCount
skippedCount
failedCount
```

接口不得继续使用“按业务类型更新全部失败任务”的现有语义。
